## Concurrencia y apagado medidos

API con **1 CPU, 512 MiB y concurrencia 2**, una réplica. Pico cgroup antes del apagado: **267.526.144 bytes = 255,13 MiB**. Las muestras docker stats, con CPU y memoria observadas, están en el resumen. Justifica comenzar con 2 como valor conservador para esta carga, dejando margen frente a 512 MiB. No establece capacidad máxima ni un límite de memoria para cualquier Markdown upstream. Configuración Python local conserva 0; Compose y .env.example usan 2; 0 desactiva explícitamente el límite.

- Carga breve C1, original repetido: 24 respuestas existing, 0 errores, 5,17 s, 4,64 req/s; p50 97,51 ms, p95 125,71 ms.
- Carga C2 de documentos nuevos: dos variantes del original identificadas por comentarios PDF después de EOF, ambas 200 extracted; 1.174,53 y 1.839,61 ms. Son variantes para checksum nuevo, no se afirman como el original sin modificaciones.
- Repetidos C2: 26 existing, 0 errores, ventana de envío de cinco segundos; p50 272,93 ms y p95 601,16 ms. Dos solicitudes de muestra no constituyen un percentil de capacidad de extracción.
- Una corrida exploratoria anterior recibió 503 al superponer dos documentos nuevos, con MAX_IN_FLIGHT=1 del Extractor de prueba. El probe inicial exigía incorrectamente todos 200 y falló; se corrigió para registrar saturación sin reintentar. La corrida final tuvo dos 200 por su temporización. No se oculta la observación previa ni se promete que ambas siempre serán aceptadas.
- SIGTERM real durante recepción parcial: la solicitud completó con 200 existing; cierre del servidor confirmado por logs, 3,692 s y **exit 143**. No hubo SIGKILL. Se registró la salida real, no se convirtió en 0. La prueba PORT en reposo también salió 143, OOMKilled=false.

El servidor deja de aceptar conexiones y espera solicitudes durante shutdown; no se implementaron señales propias ni readiness especial de drenado. Esta prueba cubre una carga en curso seguida de lookup existing; no demuestra que una extracción arbitrariamente larga termine antes de los 20 s. El cierre del AsyncClient compartido se verifica mediante test de lifespan.

## Guion para el profesor

«Mi API valida tipo, tamaño y plazo de recepción en memoria. Calcula SHA-256 del PDF y consulta Documents por checksum. Si existe, devuelve existing sin llamar al Extractor. Si falta, envía el PDF binario al Extractor, valida su respuesta y guarda content/page_count en Documents. El 201 indica extracted; 200 o recuperación de un 409 indican existing. Mongo y la extracción pertenecen a otros servicios.

Separé frontera HTTP, orquestación, clientes y modelos para que cada capa tenga una responsabilidad; los protocolos existentes permiten probar el flujo sin red. No agregué Redis ni reintentos de POST. El límite incluye multipart, la recepción tiene deadline y la admisión protege recursos con 503 inmediato. Verifiqué cancelación y cierre del cliente compartido.

Probé el flujo real con el original de 279 páginas, deduplicación, persistencia, errores y un Traefik exclusivo. Registré commits, imágenes y límites; la API consumió aproximadamente 255 MiB de pico en la carga breve con dos solicitudes. Esto respalda la configuración inicial, pero no certifica el despliegue grupal ni sustituye el benchmark del Extractor».
